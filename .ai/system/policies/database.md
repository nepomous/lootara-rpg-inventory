# POL-DB — Database

- **TRIGGER:** Schema, migrations, queries, or the data-access layer changes. Always T2.
- **WHY:** Local or remote data is the user's asset; schema mistakes are hard to undo and can corrupt existing installs.
- **VERIFY:**
  1. Schema change ↔ migration generated by the project's migration tool and included in the diff; never hand-edit generated migrations without a recorded reason.
  2. Queries use the project's designated data-access layer and query builder; no raw SQL when the project forbids it.
  3. Referential behavior (cascade/restrict) matches the business rule; verify what happens to dependent rows on delete.
  4. Existing-data compatibility: the migration runs on a populated database; new non-null columns have defaults/backfill.
  5. Types derive from the schema (TS-003).
  6. Failure path: what happens if the migration fails at app start?
  7. Data-loss risk is stated in the plan, with rollback or recovery notes.
- **EVIDENCE:** Migration file reference; test or manual script that exercises the migration on existing data; cascade verification.
- **OWNER:** Architect plans · Developer executes · QA tests with pre-populated data · Reviewer confirms.
- **ORIGIN:** legacy "Banco de Dados (Drizzle + expo-sqlite)" (tool names moved to the project).
